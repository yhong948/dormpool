# 产品与商业说明

> 对应题目提交清单第 2、5、6 项：设备清单、产品与应用说明、商业可行性简述。
> 所有成本数字均为**标注假设的估算**，非实测报价。

---

## 1. 目标用户与真实需求

### 1.1 谁会用

| 用户 | 场景 | 为什么不用单机 / 云 GPU |
|------|------|-----------------------|
| **高校实验室 / 科研小组**（3–10 人） | 跑参数扫描、批量数据预处理、小规模推理 | 单机跑一晚也跑不完；云 GPU 按小时计费，一个学期的常规批处理开销可观，且申请预算流程慢 |
| **小型设计 / 摄影工作室** | 每个项目一次性导出几百张图的缩略图、水印、格式转换 | 设计师的机器白天要开着做图，晚上闲置；买专用渲染机利用率低 |
| **课程项目团队** | 学生课程作业需要批量处理 | 学生没有预算租云，但每个人手上都有笔记本 |
| **个人开发者 / 独立开发者** | 训练集预处理、批处理脚本 | 云上跑批处理的出网流量费和实例启动开销常超过实际计算费 |

### 1.2 共同特征

这些用户的算力需求有三个特点，恰好是集中式云服务不擅长而"身边设备池"擅长的：

1. **突发性强**——平时几乎不用，偶尔要连续跑几小时。
2. **任务可拆分**——一次处理 500 张图，天然能切成 100 份。
3. **对绝对速度不敏感，对总成本和省事敏感**——晚两小时出结果没关系，但要能一键提交、结果自动汇总。

### 1.3 本原型解决的具体问题

一个 zip 包（内含图片）→ 统一入口提交 → 自动切分 → 多台设备并行处理成 128px 缩略图 → 一个结果 zip 下载。每张图带 SHA-256，结果可逐条核验。

选择这个工作负载不是因为它是最终形态，而是因为它同时满足"真实有用"和"结果可验证"：评委给一张没见过的图，系统必须算对，且改动任何一个字节都能被校验器发现。

## 2. 设备清单

### 2.1 本次演示的设备

| 项 | 值 |
|----|-----|
| 设备数量 | 1 台物理机（以 2 个独立 Worker 进程模拟 2 台从机） |
| CPU | 16 物理核 |
| 内存 | 31.78 GB |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU，8.0 GB 显存 |
| 操作系统 | Windows 11 |
| Python | 3.12 |
| 网络 | 全部 `127.0.0.1` 回环，无跨机流量 |
| Master 位置 | 与 Worker 同机 |

> **必须说明的边界**：同机双进程能证明调度、隔离、故障恢复、动态自治全部有效，但**不能**证明跨物理机的加速。两个 Worker 共享一颗 CPU，聚合效率受单机上限约束，实测 η_pool 约 65–90%，S 约 1.2–1.5。

### 2.2 真实多机部署需要什么

| 项 | 要求 |
|----|------|
| Master 主机 | 一台长期在线、成员都能访问的设备 |
| Worker | 任意安装了 Python 3.12 + `requirements.txt` 的机器 |
| 网络 | 同一局域网，或受控 VPN；Worker 只出站连接 Master |
| 端口 | 只需 Master 侧一个端口（默认 8000） |
| 每台 Worker 的工作目录 | 必须不同（`WORKER_DATA`），互不干扰 |

代码本身没有改动需求：把 `MASTER_URL` 指向 Master 的局域网 IP 即可。

## 3. 产品体验与差异化

### 3.1 完整用户流程

```
打开 http://<master>:8000/console
  → 选任务类型 image_thumb
  → 上传含图片的 zip
  → 看到 job_id 与任务数
  → 进度条自动刷新（3 秒一次）
  → 状态变"完成"，出现下载链接
  → 下载 result.zip，内含缩略图 + manifest.json
```

全程用户不需要知道有几台机器、哪台在处理、任务怎么切的。

### 3.2 贡献者视角

```bash
$ python worker/main.py
dormpool> status
  contrib_state : available
  slots         : 1 busy / 0 free
  cpu           : 42.3%
  gpu           : 47.0%

dormpool> pause
Paused — 完成手上的任务后停止接收新任务。

dormpool> resume
Resumed.
```

关键设计：**暂停不是杀死正在跑的任务**。系统进入 `draining`（还在收尾）→ `paused`（完全空闲），所以贡献者按下暂停不会丢掉已经算了一半的工作，也不会因为强行中断而浪费电。

### 3.3 与替代方案的对比

| 维度 | DormPool（本项目） | 单机跑 | 云 GPU / 云批处理 | 现成工具（Ray/Dask） |
|------|-------------------|--------|------------------|---------------------|
| 上手成本 | 装 Python + 一行命令 | 最低 | 需账号、计费、网络策略 | 需部署集群或配 K8s |
| 边际成本 | 电费 | 电费 | 按小时计费 | 服务器固定成本 |
| 数据出网 | 不出局域网 | 不出 | **要出**（隐私风险） | 视部署 |
| 资源弹性 | 谁在线用谁 | 无 | 强 | 强 |
| 对个人使用的影响 | **可暂停、可限并发** | 无 | 无 | 无专门保护 |
| 结果可核验 | 逐条 SHA-256 | — | 视服务商 | 无内建 |

**差异化落点**：不是"比云快"，而是"用自己的设备、数据不出门、且随时能停"。在实验室和工作室这种"设备都在同一屋檐下、但白天各有各的用途"的场景里，这个组合是云服务和单机都不提供的。

## 4. 成本估算（标注假设）

### 4.1 假设

- 团队 5 台设备，平均每台待机功耗 40 W，满载 150 W
- 电价 0.6 元/度（国内商业用电约 0.5–0.9 元/度）
- 每月集中批处理 30 小时，其中设备满载 20 小时
- 带宽走校园网/家庭宽带，视为已付

### 4.2 对比

| 方案 | 月成本 | 说明 |
|------|--------|------|
| **本方案** | 约 45 元 | 5 台 × 20 h × 150 W × 0.6 元/kWh ≈ 90 kWh → 54 元；扣掉设备本来就要开机的部分，净增约 **45 元** |
| 云 GPU（单卡 RTX 4060 级别） | 约 600–1200 元 | 按 2–4 元/小时 × 30 h 估算，且数据出网另计 |
| 采购专用工作站 | 8000–15000 元一次性 | 利用率通常低于 10% |

**结论**：在这个使用强度下，设备池的月成本是云 GPU 的 4–10%，且没有数据出网风险。真正的成本不在电费，而在**运维**（见下）。

### 4.3 隐性成本（诚实列出）

| 成本 | 量级 | 缓解方式 |
|------|------|---------|
| 运维：Master 要一直在线 | 一台闲置机器或一台常开 PC | 单 Master 已在设计边界内接受；后续可用 systemd/任务计划自启 |
| 成员机器的环境差异 | 每台都要装依赖 | `requirements.txt` 固定版本；后续可打包成单文件 exe |
| 网络配置 | 需要知道 Master 的 IP | 局域网内固定 IP 或 mDNS；后续做扫码/一键接入 |
| 信任成本 | 需要设备所有者同意 | 本地可随时暂停 + 只跑预定义任务（无任意代码执行） |
| 机器关机/休眠 | 任务要重跑 | 已有租约 + 自动重派 + 不双计 |

## 5. 首批用户与推广路径

### 5.1 最早的 3 个用户（可直接触达）

1. **本校本实验室**——先解决自己组的批处理，有真实负载、真实反馈。
2. **相邻课题组的同期需求**——同一栋楼，网络环境一致，接入成本最低。
3. **课程项目团队**——学期初集中出现批量处理需求，且没有预算，转化门槛低。

### 5.2 推广方式（低成本）

| 方式 | 说明 |
|------|------|
| 一个 zip 包 + 一行命令 | 不发安装包，发 GitHub Release，`python worker/main.py` 即可加入 |
| 演示即推广 | 现场用对方的图跑一遍，2 分钟出结果 |
| 按课题组为单位推广 | 一个组 3–5 台机器，天然形成一个小池子；不需要跨组打通 |

### 5.3 待验证的商业假设

| 假设 | 验证方式 |
|------|---------|
| 实验室确实有周期性批量处理需求，且现有方式痛点明显 | 访谈 3 个课题组，量化"上次等了多少小时" |
| 成员愿意在闲置时贡献算力 | 观察一个月的实际在线时长占比 |
| 暂停/恢复机制足够，不影响日常工作 | 贡献者主观评分 + 本机响应延迟对比 |
| 数据不出局域网是决策因素 | 询问是否会因为隐私问题拒绝云方案 |

**不成立的风险**：如果多数人觉得"直接跑一晚就行"，说明需求强度不足以支撑产品化——这是最需要早期验证的假设。

## 6. 从原型到产品的差距

| 维度 | 现在（原型） | 产品化需要 |
|------|-------------|-----------|
| 部署 | 手动装 Python 依赖 | 单文件可执行 / 一键安装包 |
| 状态持久化 | 内存，重启丢失 | SQLite 落盘，重启恢复 |
| 工作负载 | 一种（批量缩略图） | 插件式负载注册 |
| 多机验证 | 同机双进程 | 真实 2+ 台设备实测 |
| 接入体验 | 手填 IP | 邀请码 / 二维码 |
| Master 可用性 | 单点 | 定期备份 + 快速重建（非 HA） |
| 计费/配额 | 无 | 团队内配额与用量统计 |

这些都不改变核心架构——`Job/Task/Attempt` 模型、Worker 主动拉取、三维状态、租约与唯一确认，是已经在原型里跑通并验证过的骨架。
