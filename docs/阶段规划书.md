## 一、背景与目标

### 1.1 原型必须证明的四件事

这个原型不是"能跑起来的分布式系统"，而是要证明一个可被评委当场质疑、当场验证的主张：**一堆分散的、随时会离开的个人设备，可以像一个统一算力池一样稳定地完成真实计算，并且确实比单机快。**

把主张拆成四条可验证的判据：

| 编号 | 要证明什么 | 反例（必须能排除） |
|---|---|---|
| P1 | **两台以上设备在算真活** | 演示时只有一台机器在跑；另一台只是"在线"但没有产生任何 `SUCCEEDED` Attempt |
| P2 | **存在统一入口** | 用户要分别连两台机器；结果由人手工合并 |
| P3 | **结果正确** | 输出能下载但内容是错的/缺图/尺寸不对；重复计算被计入工作量 |
| P4 | **单机 vs 算力池有实测吞吐对比** | η_pool / S 是硬编码或由"P_pool = ΣP_i"恒等式推出来的假数 |

P4 是最容易被拆穿的一条。当前 `master/app/m6_metrics.py` 的 `summary()` 里写着：

```python
p_pool = p_sum   # 池吞吐 = 各设备吞吐之和
eta    = p_pool / p_sum * 100   # 恒等于 100.0
s      = p_pool / p_max         # 恒等于设备台数 m
```

这个写法让 η_pool 永远等于 100%、S 永远等于节点数，是**数学恒等式而不是测量结果**。S5 必须把它改成：`P_i` 来自单机基准跑（G1/`executor/benchmark.py`），`P_pool` 来自池化跑的墙钟时间，两者独立测量。G6 专门守这一点。

### 1.2 冻结的工作负载

任务类型 `image_thumb`，规格已在共享上下文中冻结，此处只复述接口边界，实现细节见门禁 G1：

- Job 输入 = 一个 zip，内部平铺 `.png/.jpg/.jpeg`。
- Master 按 `SHARD_SIZE`（环境变量，默认 3）切片，产出 `data/inputs/<job_id>/shard_<i>.zip`，`input_ref = "inputs/<job_id>/shard_<i>.zip"`。
- Executor 对每张图：Pillow 打开 → `convert("RGB")` → `thumbnail((128,128), Image.LANCZOS)` → 存 PNG 到输出 zip 的 `thumbs/` 下；同时写 `manifest.json`（`input_name/input_sha256/output_name/output_sha256/out_w/out_h` 的 JSON 列表）。
- `units_done = len(manifest)`。
- **确定性**：同输入字节 → 同输出字节（同机）。

### 1.3 18 小时约束带来的取舍

18 小时意味着大约 6 个可交付阶段，每个阶段 2–3.5 小时，且必须留 2.5 小时做集成与彩排。由此确定三条硬取舍：

1. **状态全在内存**。不做持久化，Master 重启即丢 Job。18 小时内做持久化会挤占 S3/S4 的主链路时间。
2. **不做能力匹配调度**。`resource_req` 只填 `{"gpu": False}`，M4 只做 FIFO + 槽位判断，不做 GPU 亲和。
3. **只支持一种 task_type**。`TASK_REGISTRY` 只有一个键。多 workload 是演示之后的事。

### S0 · 契约冻结（H0–H1.0，1.0h）

**目标**：让三个人在写第一行业务代码之前，对"数据怎么流、字段叫什么、谁负责哪个文件"没有分歧。S0 之后任何契约变更都要全员同意并单独提交，本阶段磨刀不误砍柴。

**交付物**

- `shared/contracts.py` 保持不动（已含全部所需类型与常量：`HEARTBEAT_INTERVAL=10`、`LEASE_DURATION=120`、`LEASE_RENEW_BEFORE=20`、`WORKER_TIMEOUT=35`、`MASTER_PORT=8000`、`EXECUTOR_*`）。S0 的产出不是改它，而是**确认它够用**。
- 一页接口对照表（写进 `docs/log/` 各自模块日志即可，不新建文档），锁定以下 9 条决策：
  1. `submit_job` 用 multipart：字段 `task_type`（form）+ `file`（file），不用 query 参数。现有 `m1_api.py` 把 `task_type` 写成 query 参数，必须改。
  2. 分片：`SHARD_SIZE` 环境变量，默认 3；`input_ref` 形如 `inputs/<job_id>/shard_<i>.zip`。
  3. `data/` 根目录可用 `DORMPOOL_DATA` 覆盖，默认 `data`；Worker 本地目录 `WORKER_DATA`，默认 `worker_data`。
  4. 鉴权：`DORMPOOL_TOKEN` 非空时，除 `GET /ping` 与 `GET /console` 外全部要求 `Authorization: Bearer <token>`。**禁止**把 token 回显到响应体。
  5. `GET /ping` 无鉴权，返回 `{"ok": true, "ts": <epoch>}`。
  6. **C3 验证器的归属**：遵循仓库既有决定（见 `资源结构分析.md`："结果验证骨架原放在 `executor/workload/`，现移至 `master/app/c3_validation.py`：Master 才拥有结果确认与有效工作量计数的最终权威"）。因此：
     - **权威校验器在 `master/app/c3_validation.py`，由 A 实现**（`ImageThumbValidator.validate()`：重开 zip、逐条核对 `input_sha256`/`output_sha256`/尺寸、返回确认后的 `units_done`）。它跑在 Master 上，不随 Worker 分发。
     - **C 在 `executor/` 下提供一个独立复算脚本**（如 `executor/tools/check_output.py`），只用于测试交叉验证，**不参与**生产确认路径。两套独立实现互相印证，比一套更能说明"结果真的对"。
     - 这样避免了把校验逻辑塞进要分发到各台学生电脑上的 `executor/`——那会让"Worker 自己决定自己结果有效"重新成立，正是既有文档要修掉的问题。
  7. Worker 的 `--worker-id` 与 `WORKER_ID` 环境变量等价，后者优先；未设置时用 `hostname + "-" + uuid4().hex[:6]`。
  8. Executor 退出码语义：`2`（fatal）时 Worker 不上传、不重试；`1`（task fail）时 commit `error_msg` 并允许 Master 重试。
  9. Console 由 Master 在 `GET /console` 提供，路径基于仓库根目录解析（见风险 R4）。

**负责人**：全员，A 作为仲裁人落笔。**门禁**：G0。

**S0 出口条件**：G0 全绿，且三人各自在模块日志里写下"已确认第 1–9 条"。

### S1 · 单机计算（H1.0–H3.5，2.5h）

**目标**：在完全没有网络的情况下，`python executor/run.py image_thumb <shard> <out>` 能对一个真实 shard 产出正确、可校验、可重现的结果。这是整个系统唯一真正"干活"的地方，必须先于任何网络代码立住。

**交付物**

| 文件 | 负责人 | 内容 |
|---|---|---|
| `executor/workload/image_thumb.py` | C | `run(input_path, output_path) -> int`。解压 shard → 逐图处理 → 写 `thumbs/` + `manifest.json` → 返回 `len(manifest)` |
| `executor/run.py` | C | `TASK_REGISTRY = {"image_thumb": image_thumb.run}`；异常分支保证 stdout 最后一行仍是契约 JSON |
| `master/app/c3_validation.py` | A | **权威 C3 校验器**：`ImageThumbValidator(ResultValidator)` 重开输出 zip，逐条核对 `input_sha256`/`output_sha256`/尺寸，返回确认后的 `units_done`，异常抛 `ValidationError`；注册进 `VALIDATORS` |
| `executor/tools/check_output.py` | C | 独立复算脚本（测试用，非生产路径）：用不同代码路径重算一遍 manifest，供 G1/G4 交叉验证 |
| `executor/benchmark.py` | C | 单机串行跑 N 个 shard，输出 `task_type/total_tasks/units_done/elapsed_s/throughput` 的 JSON——这是 P_i 的唯一合法来源 |
| `executor/tools/make_sample_zip.py` | C | 确定性样例图生成器，供 G1/G3 复用，避免每次手搓图片 |

**关键实现约束（写进代码注释，防止后来者破坏）**

- `thumbnail()` 会**原地修改**图像对象，且只缩不放（小图不放大）。这两点都要在 manifest 里如实反映 `out_w/out_h`。
- 确定性三件套：`sorted()` 遍历 zip 内文件名；写 zip 时用固定 `ZipInfo(date_time=(1980,1,1,0,0,0))` 而不是 `ZipFile.write()`（后者会把源文件 mtime 写进归档，两次运行字节不同）；`manifest.json` 用 `sort_keys=True, separators=(",",":")` 且不依赖 dict 插入顺序。
- 不允许 `Image.open().save()` 直接透传 EXIF 方向导致同图不同果；先 `convert("RGB")` 再处理。
- 命名冲突：zip 内若出现同名不同路径图片，按 `input_name` 排序后处理，重名时输出名追加 `_<序号>` 并在 manifest 里可追溯。

**负责人**：C 主，A 一行集成。**门禁**：G1。

**S1 出口条件**：G1 全绿（含确定性子项），`benchmark.py` 能产出一次真实的 P_i 数字并记录到日志。

### S2 · 节点接入（H3.5–H6.0，2.5h）

**目标**：Master 起来能被 `curl` 访问；Worker 起来能注册、发心跳、上报真实硬件能力；杀掉 Worker 后 Master 能在一个 `WORKER_TIMEOUT` 内把它标成 OFFLINE。**本阶段不涉及任何任务**，只管"人到了没有"。

**交付物**

| 文件 | 负责人 | 内容 |
|---|---|---|
| `master/app/m1_api.py` | A | `GET /ping`（无鉴权）、`POST /workers/register`、`POST /workers/{id}/heartbeat`、`GET /workers`；统一 `verify_token` 依赖 |
| `master/app/m2_registry.py` | A | `register`（新建 vs 重连）、`heartbeat`（三维状态写入）、`list_workers`、`_expire_loop`（`WORKER_TIMEOUT` 超时置 OFFLINE、`free_slots→0`） |
| `worker/agent/w3_monitor.py` | B | `detect_capabilities()`（`psutil.cpu_count(logical=False)` / `virtual_memory().total`）、`_detect_gpu()`（`pynvml` 优先，无则 `(None,None)`，**不 import torch**）、`cpu_pct()`、`gpu_pct()`、槽位计数 |

| `worker/agent/w1_runtime.py` | B | 启动序列：`/ping` → 注册 → 起心跳线程 → 起任务循环；**非交互模式**（见风险 R6） |

**负责人**：A（master 侧）、B（worker 侧）。**门禁**：G2。

**S2 出口条件**：G2 全绿；`GET /workers` 里 `cpu_cores` 与机器真实物理核数一致（不是写死的），`gpu_name` 在本机无卡时为 `null` 而不是字符串 `"None"`。

### S3 · 任务分发（H6.0–H9.5，3.5h）

**目标**：提交一个 zip，Master 把它切成 N 个 shard，两个 Worker 各自领到**不同**的任务，各自跑出结果并上传。这是全项目第一个真正跨进程的链路，也是最容易出并发 bug 的地方。

**交付物**

| 文件 | 负责人 | 内容 |
|---|---|---|
| `master/app/m3_job.py` | A | `create_job`：解 zip → 按 `SHARD_SIZE` 切片落盘 → 建 N 个 Task；`mark_task_succeeded/failed`；进度与终态判定 |
| `master/app/m4_scheduler.py` | A | `assign_task`（**持锁内**选 PENDING → 建 Attempt → 置 ASSIGNED/RUNNING，保证同一 Task 不会被两个 Worker 同时拿到）、`renew_lease`、`commit_result`、`_lease_expiry_loop` |
| `master/app/m5_data.py` | A | `GET /data/{ref}`（路径穿越防护）、`POST /data/upload/{job_id}/{task_id}`（multipart 字段 `file`）、`resolve_path` |
| `worker/agent/w2_connector.py` | B | `claim()` / `fetch_input()` / `upload_output()` / `renew_lease()` / `commit()`,均带超时 |
| `worker/agent/w5_exec.py` | B | 下载输入到 `WORKER_DATA` → `subprocess.run([sys.executable,"executor/run.py",...])` → 解析末行 JSON → 上传 → commit；续租线程在剩余 `LEASE_RENEW_BEFORE=20`s 时续；退出码 2 不重试 |

**关键实现约束**

- **领取必须是原子的**：`assign_task` 的"找任务 + 改状态 + 建 Attempt"要在同一把锁内完成。README 里说的"Worker Pull"不提供天然互斥。
- **提交路径用 `sys.executable`**，不要裸写 `python`（Windows 上可能是另一个解释器或没在 PATH）。
- **续租失败不能静默**：连续续租失败且 Master 不可达时，Worker 应在本地放弃该 attempt 而不是继续烧 CPU。
- `data/` 下所有路径拼接必须经过 `m5_data.resolve_path`，拒绝含 `..` 或绝对路径的 ref（技术点 G2）。

**负责人**：A、B。**门禁**：G3。

**S3 出口条件**：G3 全绿；一次 7 图 / `SHARD_SIZE=3` 的 Job 产生 3 个 Task，两个 Worker 各完成至少 1 个，Attempt 表里没有任何 task 被两个不同 worker 同时持有。

### S4 · 结果闭环（H9.5–H12.0，2.5h）

**目标**：用户可以只面对一个 URL —— 提交、看进度、下结果。结果不是"把 N 个 zip 丢给你"，而是一个可直接校验的合并 zip。

**交付物**

| 文件 | 负责人 | 内容 |
|---|---|---|
| `master/app/m4_scheduler.py` | A | `commit_result` 走 C3 验证 → 唯一确认（`AttemptStatus != RUNNING` 一律 `discarded`）→ 成功才累加 `done_tasks` 并写 `MetricRecord` |
| `master/app/m5_data.py` | A | `aggregate(job_id)`：把各 Task 输出 zip 的 `thumbs/*` 合并进最终 zip，`manifest.json` 用列表合并并**按 `input_name` 排序**，写 `outputs/<job_id>/result.zip` |
| `master/app/m3_job.py` | A | `done_tasks == total_tasks` → `COMPLETED` + `finished_at` + `output_ref` |
| `master/app/m1_api.py` | A | `GET /jobs/{id}`、`GET /jobs/{id}/result`（`FileResponse`，`application/zip`）、`GET /jobs` |
| `console/index.html` | C | 提交表单、Job 列表轮询（2s）、状态徽章、进度条、结果下载链接、Worker 卡片 |
| `worker/agent/w5_exec.py` | B | 上传失败的重试与本地残留清理 |

**关键实现约束**

- **合并去重**：两个 Task 理论上可能产出同名 `thumbs/x.png`（分片不应发生，但聚合层不能假设）。合并时若 `input_sha256` 相同则视为同一图去重，不同则报错——宁可暴露 bug 也不静默覆盖。
- **进度单调**：`done_tasks` 只增不减；重试成功后不能二次自增（用 Task 状态迁移而非计数增减来驱动）。
- **下载必须 200 + 正确长度**：`Content-Length` 与文件大小一致，`curl -o` 后 `unzip -t` 通过。

**负责人**：A 主、C 控制台、B 上传链路。**门禁**：G4。

**S4 出口条件**：G4 全绿；最终 zip 的 `manifest.json` 条数 == 提交图片数，逐条 `output_sha256` 与独立复算一致。

### S5 · 动态自治与指标（H12.0–H15.5，3.5h）

**目标**：向评委演示"人会走，池不会崩"——暂停、恢复、中途加入、进程被杀，任务最终都收敛。同时产出真实的 η_pool / S。

**交付物**

| 文件 | 负责人 | 内容 |
|---|---|---|
| `worker/agent/w4_contrib.py` | B | `pause()/resume()`、`state()`（`AVAILABLE/DRAINING/PAUSED`）、`can_accept()`；产出变化在**下一次心跳**内反映到 Master |
| `worker/agent/w6_control.py` | B | REPL：`status/pause/resume/quit`，且在非 tty 下可被 stdin 脚本驱动（G5 自动化需要） |
| `master/app/m2_registry.py` | A | OFFLINE 时回调 `m4_scheduler.reclaim_worker(worker_id)` |
| `master/app/m4_scheduler.py` | A | `reclaim_worker`（把该 worker 的 RUNNING attempt 置 EXPIRED、task 回 `RETRY_PENDING`）；I4 迟到结果丢弃；`max_retries` 用尽置 FAILED |
| `master/app/m6_metrics.py` | A | **重写 `summary()`**：`P_i` 来自单机基准、`P_pool` 来自池化窗口墙钟、`eta_pool_pct = p_pool/ΣP_i*100`、`S = p_pool/max(P_i)`；仅统计 `SUCCEEDED`；节点事件 join/pause/resume/leave/timeout |
| `master/app/m1_api.py` | A | `GET /metrics/summary` |
| `console/index.html` | C | 节点事件时间线、每设备吞吐条、η_pool / S 卡片 |
| `executor/benchmark.py` | C | 补 `--pool` 模式，输出可喂给 M6 的 P_pool 实测值（或确认池化由真实 Job 跑出） |

**关键实现约束**

- **暂停语义**：`DRAINING` 是"已暂停但还有活在跑"，不是中间态装饰。Master 侧看到 `PAUSED/DRAINING` 时**不再给该 worker 派任务**，靠 `claim` 接口的返回值为空实现，不要靠调度器猜测。
- **杀进程后不许双计**：worker 被杀 → OFFLINE → task 回 RETRY_PENDING → 另一台重跑成功。原 attempt 若随后"复活"提交结果，必须因 `AttemptStatus=EXPIRED` 被 `discarded`。G5 专门检查 `SUM(units_done) == total images`（不是 2 倍）。
- **指标只信成功 attempt**：`MetricRecord` 在 `commit_result` 成功分支写入，且只在 Task 从非 SUCCEEDED 迁到 SUCCEEDED 的那一次写。重试成功的 attempt 也计入（它确实干了活），但同一 attempt 不重复计入。
- **eta_pool 不许 > 110%**：超过说明窗口或分母不一致，应当暴露成异常而非粉饰。

**负责人**：A（M2/M4/M6）、B（W4/W6）、C（console）。**门禁**：G5、G6。

**S5 出口条件**：G5、G6 全绿；至少完成一次真实的两进程暂停/恢复/杀进程实验并留证。

## 四、本地仿真策略（127.0.0.1 双进程）

### 4.1 为什么仿真

18 小时内不可能反复借到两台配置一致的真机做回归。所有门禁 G0–G6 必须能在**一台 Windows 机器上、只绑 127.0.0.1** 的条件下全绿，否则 CI、复现、排障都无从谈起。

### 4.2 拓扑

```
                        127.0.0.1:8000
                 ┌─────────────────────────┐
                 │  Master (uvicorn)       │
                 │  data/                  │
                 │   ├ inputs/<job_id>/    │
                 │   ├ outputs/<job_id>/   │
                 │   └ uploads/            │
                 └───────┬────────┬────────┘
                         │        │
              ┌──────────▼──┐  ┌──▼──────────┐
              │ worker-A    │  │ worker-B    │   ← 两个独立进程，独立 PID
              │ WORKER_DATA │  │ WORKER_DATA │
              │ =data/worker_data/worker-A │ =.../worker-B
              │ MAX_SLOTS=1 │  │ MAX_SLOTS=1 │
              └─────────────┘  └─────────────┘
                    │                 │
              executor 子进程    executor 子进程   ← 各自独立，崩溃互不影响
```

**必须满足的仿真纪律**

1. **只绑 127.0.0.1**：`--host 127.0.0.1`，绝不 `0.0.0.0`。收工前 `netstat -ano | grep :8000` 必须为空。
2. **两个进程真的独立**：不同 `WORKER_ID`、不同 `WORKER_DATA` 目录、不同 PID。禁止用线程模拟"两个节点"——那证明不了进程隔离，也测不出真实的子进程开销。
3. **`MAX_SLOTS=1`**：一台机器两个 worker 各 1 槽，避免同机 CPU 争抢把"池化加速"测成噪声。
4. **数据目录互不覆盖**：`DORMPOOL_DATA=data`（Master），`WORKER_DATA=data/worker_data/worker-<X>`（各 Worker）。
5. **端口占用即失败**：起 Master 前先检查 8000，起 Worker 前不额外监听端口（Worker 只做出站）。

### 4.3 仿真的诚实边界（必须写进演示材料）

同机双进程证明的是**调度、隔离、容错、聚合的正确性**，证明不了**物理并行带来的真实加速**。两个进程共享同一颗 CPU，η_pool 会显著低于 100%，这不是系统缺陷而是物理事实。

因此：

- **G1–G5 在仿真环境判定**，全部可自动复现。
- **G6 的数字必须标注测量环境**："单机双进程仿真"下的 η_pool 只用于**验证公式与管线正确**，不得当作对外宣称的加速比。
- **最终演示仍必须证明两个独立进程各自做了真实工作**，证据链（缺一不可）：
  1. `GET /workers` 同时列出 `worker-A` 与 `worker-B`，`cpu_cores/ram_gb` 为真实嗅探值；
  2. 一次 Job 的 Attempt 记录里，两个 `worker_id` 各有 ≥1 条 `SUCCEEDED` 且 `units_done > 0`；
  3. 两个进程的 PID 不同（`tasklist`/控制台可见），且各自拉起过独立的 executor 子进程；
  4. 最终 `manifest.json` 中可追溯到来自两个 shard 的图片。
- **若能在真机上跑，优先跑真机**，仿真数据仅作为回归基线。对外口径统一为"同机双进程仿真 + 真机两台验证"两层，不混为一谈。
