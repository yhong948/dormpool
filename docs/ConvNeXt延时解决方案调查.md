# ConvNeXt 延时解决方案调查

## 结论

优先采用每张 GPU 一个常驻 Executor 进程，启动时加载权重并预热，连续处理多个 Task。
先保持一次只执行一个 Task，再使用每个 Task 8 张图片的批量作为调优起点。
8 是本机合成图片实验的起点，需要以真实图片的端到端数据确认，不能作为所有设备的固定最优值。

扩大分片能立即摊薄初始化成本，但每个 Task 新建进程的根因仍然存在。
提高槽位数会复制模型、CUDA 上下文和 CPU 线程，无法替代模型复用。
当前启动脚本 `MaxSlots` 默认值为 100，与注释的 1 不符；进行 GPU 测试时应明确传 `-MaxSlots 1`。

## 本地测量

设备：RTX 5060 Laptop GPU，约 8 GB 显存；Python 3.14，PyTorch 2.15.0+cu132。
使用项目现有 `convnext_infer.run()` 和本地权重，在同一进程中对每种批大小预热后运行 3 次，取中位数。
输入为相同内容的 640×480 合成 PNG；计时包含 ZIP 读取、Pillow 预处理、CUDA 推理、结果回传到 CPU 与 ZIP 写出，
不包含 HTTP、Master 调度、结果验证和服务端汇总。

| 每个 Task 图片数 | 热任务中位耗时 | 图片/秒 | 峰值张量显存 MiB |
|---|---:|---:|---:|
| 1 | 17.58 ms | 56.9 | 206.2 |
| 4 | 41.20 ms | 97.1 | 241.7 |
| 8 | 73.50 ms | 108.8 | 288.9 |
| 16 | 144.69 ms | 110.6 | 386.4 |

本次模型冷初始化约 3.88 秒；前次测量为 6.71 秒，说明冷启动会随系统及缓存状态波动。
峰值张量显存只统计 PyTorch 分配的张量，不等于整个进程或显卡总占用。
热任务数据证明复用模型值得实施，不代表最终服务可以达到表中的吞吐。
实验脚本在工作区 `._tmp/compare_convnext_batches.py`，生成的输入输出也位于 `._tmp/`。

## 方案比较

| 方案 | 收益 | 主要代价 | 采用顺序 |
|---|---|---|---|
| 增大 `ShardSize` | 多张图分摊一次冷启动 | 暂停响应、失败重算粒度变大；整个分片当前一次进入显存 | 可先用作临时缓解 |
| 常驻子进程 | 框架、模型和 CUDA 上下文跨 Task 复用 | 要实现进程健康检查、请求协议、超时重启和退出清理 | 首选改造 |
| 在 Agent 内直接推理 | 也能保留模型 | CUDA 异常或内存问题影响 Agent；超时难单独终止 | 不优先采用 |
| 一个常驻进程合并多个 Task 的微批 | 更好地利用 GPU | 增加排队、结果拆分、租约和失败处理复杂度 | 常驻方案稳定后再考虑 |
| AMP、channels-last、`torch.compile` | 可能改善纯推理耗时 | 要重测精度、输出和设备兼容性；编译存在额外冷启动 | 先解决生命周期再评测 |

## 适合当前代码的实现边界

1. **Executor 增加常驻模式**：保留现有单次 CLI，新增读取 JSON Lines 请求的模式。
   请求包含 `task_id`、`attempt_id`、任务类型及本地输入输出路径，响应包含相同 ID、成功状态、有效工作量和错误。
   stdout 只用于协议消息并及时 flush；stderr 独立持续消费并实时写日志，避免管道写满。
2. **W5 管理进程生命周期**：每张 GPU 一个执行进程，每次只交付一个 Task。
   IPC 传文件路径，不传模型和 GPU Tensor；任务的上传、提交及租约仍由 Agent 负责。
   常驻进程不再使用等待退出的 `communicate()` 作为任务结束信号，应改为读取带 ID 的响应，并为单任务设置超时。
3. **注册前完成初始化**：由将要执行任务的常驻进程加载模型、预热并报告设备与能力。
   当前 W2 的 `backend_summary()` 会把模型加载到 Agent，而实际子进程又加载一份，改造时应去掉这份重复加载。
4. **槽位与后端容量一致**：单 GPU 先设一个 GPU 执行槽位；不要先领取 50 个 Attempt 再排队等同一个 GPU。
   若以后让同一 Worker 同时处理 CPU/GPU 工作负载，需要分别管理容量，避免通用 `MaxSlots` 被误当作 GPU 并发数。
5. **批量显存上限**：`ShardSize` 是调度/重试单位，GPU batch size 是显存控制单位，应分开配置。
   先选 8 图分片；若支持更大分片，执行器内部按 batch 上限分块推理，避免一次将整个分片堆入 GPU。

## 故障与自治语义

- 从领取 Attempt 起就维护租约，覆盖下载和执行时间；当前续租线程在子进程启动后才开始，下载很慢时存在空窗。
- 输入损坏等普通任务错误可以返回失败并继续服务下一任务。
- CUDA 上下文损坏、进程崩溃或任务超时，应终止并重建该 Executor；当前 Attempt 通过 Master 的有限重试恢复。
  不在执行器内部悄悄重跑并重复提交，不自动切到 CPU。
- 任务完成以带 ID 的协议响应为准；响应丢失可能导致重算，最终有效结果仍由 Master 对逻辑 Task 唯一确认。
- 手动暂停立即停止新领取，当前任务完成后保留可恢复状态；可以提供独立的卸载模型操作以释放显存。
- 退出时先停止领取、等待在途任务或到达明确退出超时，再关闭 IPC、终止并回收子进程。
  当前任务线程是 daemon，`shutdown()` 仅设置标志，需要补齐真正的等待与清理。
- 按进程设置合理 CPU 线程上限，预处理和编码仍会使用 CPU；增加 GPU 并发不应无限放大 CPU 线程。

## 验收与测量

- 连续执行至少 10 个 Task，稳定期间只加载一次权重，执行器 PID 保持一致。
- 分别记录冷启动、热任务 P50/P95、排队、下载、预处理、GPU、打包、上传与确认时间。
  GPU 时间使用 CUDA Events 或显式同步测量，避免只测到异步提交耗时。
- 对同一真实输入比较旧模式与常驻模式的完整 Job 耗时、有效吞吐、CPU、RAM 和 GPU 总显存。
- 注入输入损坏、执行器退出、超时及重启，检查任务收敛、租约与唯一计数。
- 验证暂停/恢复、Worker 退出无孤儿进程，以及 CPU 缩略图回归。
- 当前验证器检查分类结果结构、哈希与输入覆盖，不能独立证明模型预测正确；
  还应使用固定输入与可信参考输出比较类别、分数或 logits 误差。

## 官方依据

- [PyTorch 多进程实践](https://docs.pytorch.org/docs/2.15/notes/multiprocessing.html)：
  CUDA 多进程应采用支持的启动方式；避免 CPU 线程过度竞争。当前项目可以继续用全新 `subprocess`，无需共享 CUDA 状态。
- [torch.compile 冷启动说明](https://docs.pytorch.org/docs/2.15/user_guide/torch_compiler/compile/programming_model.reducing_compile_time.html)：
  初次调用会支付编译成本，因此不应把编译作为解决每 Task 重启进程的第一步。
