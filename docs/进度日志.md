选定 **`image_thumb`：批量缩略图**。理由：

- Pillow 已装，无额外依赖

### 2.3 踩坑记录

- Git Bash 会把命令行参数 `/tmp/x` 自动转成 `C:/Users/.../Temp/x`，但 heredoc 里的同一字符串**不会**转，导致脚本找不到文件。统一改用仓库内相对路径 `_tmp/...` 后一致。
- 若用 `ZipFile.write()` 写归档，源文件 mtime 会进入归档；必须用 `ZipInfo(date_time=(1980,1,1,0,0,0))` + `writestr`。

### 3.3 联调中发现并修复的缺陷

| # | 现象 | 根因 | 修复 |
|---|------|------|------|
| 1 | `claim` 返回 500 `UnboundLocalError: payload` | `assign_task` 中 `payload` 只在循环体内赋值，空队列路径未绑定 | 前置 `payload = None`，循环内命中后 `break` |
| 2 | Worker 注册成功但每个任务间隔 5–10 秒 | 派活用的是**注册表缓存**的 `free_slots`，只随心跳（10s）更新 | 新增 `can_accept_work()`：只校验在线+未暂停；容量以 claim 请求体里的实时值为准 |
| 3 | 结果上传 422 Unprocessable Entity | `requests.Session` 上设了全局 `Content-Type: application/json`，覆盖了 multipart 的 boundary | Session 只保留 Authorization；JSON 头逐请求设置 |
| 4 | `python worker/main.py` 报 `ModuleNotFoundError: worker` | 直接运行包内文件时 `sys.path[0]` 是 `worker/` | 入口显式插入仓库根 |
| 5 | 暂停后 Master 最长 10 秒才看到状态 | 心跳周期 10s | `pause()/resume()` 后立即补发一次心跳 |
| 6 | 暂停后仍上报 `free_slots=1` | 心跳直接用了本地空闲槽位 | 非 `available` 状态一律上报 0 |
| 7 | η_pool 只有 9%，S=0.18 | `P_i` 分母只累加执行耗时，而 `P_pool` 用的是作业墙钟，两者口径不可比 | `P_i` 分母改为**占用跨度**（首个 attempt 开始 → 最后一个结束，下限为累加耗时） |
| 8 | 杀节点后 51.6 秒才判离线 | 扫描间隔 `WORKER_TIMEOUT/2 = 17.5s` + 超时 35s = 最坏 52.5s，超过门禁 45s 上限 | 扫描间隔改为 `min(WORKER_TIMEOUT/4, 10) = 8.75s` |

修复第 7、8 项后的指标：

```
per device: {'worker-A': 0.2428, 'worker-B': 0.2672}
p_pool=0.3347 (pool_wall_clock)  eta=65.63%  S=1.2528
```

## 4. 阶段 S5 · 动态自治（G5）

`tests/g5_dynamic.py` 覆盖暂停、恢复、热加入、杀进程四个场景。

### 4.1 最终结果

```
[G5-A] pause
    busy at done=1
    trace: [('draining','busy',0) x8 ... ('paused','idle',0)]
[G5-B] resume
[G5-C] hot join
    worker-B joined at done=3
[G5-D] kill a worker mid-task
    killed worker-A at t=1794639196
    offline after 42s
    recovered: 12 units, 0 discarded attempts

G5 ALL PASSED
{
  "G5-A": "draining->paused, done 1->2",
  "G5-B": "available again, done advanced from 2",
  "G5-C": "worker-B did 5 units",
  "G5-D": "offline in 42s, 12 units, no double count"
}
```

### 4.2 门禁语义验证

| 断言 | 观测值 | 结论 |
|------|--------|------|
| 暂停后先 `draining` 后 `paused` | trace 顺序正确 | 未杀在跑任务 |
| 暂停期间进度最多 +1 | done 1 → 2 | 只收尾手上那一个 |
| `paused` 时 `free_slots == 0` | 0 | 不虚报容量 |
| 热加入节点分到活 | worker-B 完成 5 个单位 | 剩余任务被新节点领取 |
| 杀节点后判离线 ≤45s | 42s | 满足门禁 |
| 总工作量不双计 | 成功单位合计 12 = 提交 12 | 被中断的 attempt 记 0 |

### 4.3 踩坑记录

- 测试脚本原用 `/workers` 的 `exec_state` 判断节点是否在忙，但该字段只在心跳时刷新（10s 一次），而单分片任务只跑约 1 秒，采样窗口命中率过低。改为轮询作业详情里是否存在该节点的 `running` attempt——作业状态在每次 claim 时更新，是权威来源。
- G5-D 首次失败暴露了真实的超时上限问题（见上表第 8 项），不是测试脚本问题。

## 5. 阶段 S5 · 测量（G6）

`tests/g6_measure.py` 做两次**独立**测量：单 Worker 一次，双 Worker 一次，输入完全一致。

### 5.1 结果

```
[single] only worker-A alive, 9 images
  status=completed units=9 wall=46.91s p=0.192 u/s
  summary: p_pool=0.1918 eta=90.79% S=0.9079 per_device={'worker-A': 0.2113}

[pool] both workers alive, same input
  status=completed units=9 wall=24.18s p=0.372 u/s
  summary: p_pool=0.3722 eta=83.4% S=1.5359
  per_device={'worker-A': 0.2039, 'worker-B': 0.2423}

G6 PASSED
```

### 5.2 公式回代

```
η_pool = P_pool / ΣP_i × 100%
       = 0.3722 / (0.2039 + 0.2423) × 100%
       = 0.3722 / 0.4462 × 100%
       = 83.4%                          ← 与接口返回一致

S      = P_pool / max(P_i)
       = 0.3722 / 0.2423
       = 1.5359                         ← 与接口返回一致
```

### 5.3 关键验证

| 断言 | 结果 | 意义 |
|------|------|------|
| 单 Worker 时 S≈1.0（0.9079） | 通过 | 证明 P_pool **不是** ΣP_i；否则 S 恒等于节点数 |
| `p_pool_source == "pool_wall_clock"` | 通过 | P_pool 来自作业墙钟 |
| p_pool 与独立计算 `units/wall` 相差 <15% | 通过 | 定义一致性 |
| η_pool 落在 (0, 115] | 83.4% | 数值合理 |
| 每设备吞吐只在真实出过力的节点上出现 | 通过 | 无幽灵设备 |

### 6.2 诚实说明的局限

1. **同机模拟，不是真实多机。** 两个 Worker 进程共享同一颗 CPU，聚合效率受单机算力上限约束，所以 η_pool 通常低于 100%。这证明了调度、隔离、故障恢复是有效的，但**不构成**跨物理机的加速证据。真实多机需要在两台设备上各跑一次 `worker/main.py` 并指向同一 Master。
2. **数据保存在本地磁盘，无持久化数据库。** Master 重启后内存中的 Job/Worker 状态丢失，磁盘上的 `data/` 仍在。
3. **单 Master，无高可用。** 符合方案二的既定边界。
4. **延时开关参与动态实验。** `G5/G6` 中的部分数字是在 `DORMPOOL_EXECUTOR_DELAY_MS>0` 下测得的，目的是让单任务时长足以观察暂停/热加入。真实吞吐应以 `delay=0` 的基准为准（见 `executor/benchmark.py`）。
